## Spec-Driven Development pour VerifactureBTP — mon avis honnête

On l'a **déjà en partie** sans le savoir. Regarde :

### Ce qu'on fait déjà qui EST du spec-driven

| Pratique                   | Notre version                                                |
| -------------------------- | ------------------------------------------------------------ |
| Spec API avant le code     | `shared-contracts/openapi.yaml` = source de vérité, le backend et le frontend en découlent |
| Contraintes formalisées    | `.claude/rules/` — UUID, BigDecimal, parité web/mobile, conventions API |
| Procédures de construction | `/new-endpoint` force l'ordre : OpenAPI → Backend → Frontend |
| Conformité réglementaire   | DGFiP 2026 / EN16931 — les mentions obligatoires sont des specs légales |

### Ce qu'un vrai spec-driven aurait ajouté

Pour chaque feature (ex: "gestion des avoirs"), on aurait eu un fichier `specs/avoirs.md` :

# Avoirs — Spécification technique

## Comportement
- Un avoir est lié à une facture existante
- Montant négatif, plafonné au montant de la facture source
- Numérotation séquentielle AV-{YYYY}-{NNN}

## Cas limites
- Avoir sur facture déjà soldée → refusé
- Avoir partiel → recalcul du reste à payer
- Double avoir sur même facture → autorisé si total ≤ montant facture

## Critères d'acceptation
- [ ] API POST /api/v1/avoirs retourne 201
- [ ] Montant > facture source → 422
- [ ] Liste paginée avec filtre par chantier
- [ ] Parité web/mobile

### Ce que ça aurait changé concrètement

**Les gains :**

- Moins d'allers-retours entre toi et moi ("ah non, je voulais que ça fasse X pas Y")
- Les cas limites pensés AVANT, pas découverts en prod
- Un historique des décisions ("pourquoi l'avoir partiel est autorisé ?")

**Les coûts :**

- Du temps à rédiger chaque spec avant de coder — pour un solo dev/petite équipe, c'est lourd
- Des specs qui deviennent obsolètes si on ne les maintient pas (un fichier de plus à mettre à jour)
- Le risque de sur-spécifier des features simples

### Mon verdict pour VerifactureBTP spécifiquement

**Ça aurait été overkill pour 80% du projet, mais aurait évité des galères sur les 20% restants.**

Les trucs simples (CRUD chantiers, liste factures, fournisseurs) — le combo openapi.yaml + rules + skills suffit largement. Pas besoin d'une spec de 50 lignes pour un CRUD.

Mais les trucs complexes :

- **Situations de travaux** (acomptes, retenue de garantie, calculs progressifs) — on a eu des allers-retours et le bug CQRS projection qu'on traîne encore
- **Conformité DGFiP** (mentions obligatoires, chaîne de hash, archivage) — les cas limites réglementaires auraient mérité une spec formelle
- **Auth JWT self-issued** — la matrice de priorité (JWT_SECRET > JWT_ISSUER_URI > permitAll) aurait été plus claire dans une spec

### Ce que je te recommande

Pas du spec-driven pur (trop lourd pour ton rythme), mais un **"spec-on-demand"** :

> Pour toute feature qui touche à du **calcul**, de la **conformité réglementaire**, ou de la **logique multi-étapes** — prends 5 min pour écrire les cas limites et critères d'acceptation AVANT de me demander de coder.

Pour le reste (pages, CRUD, UI) — continue comme maintenant, ça marche très bien.

Tu veux qu'on mette en place un template `specs/` pour les features complexes à venir ?
